# Disable one invited application account

The protected **People and permissions** view can disable one accepted local invitation account. The permanent platform owner must have a current MFA session, review the exact application/user/invitation and confirm a separate artifact approval. This action cannot be consumed by code publication, rollback, another user or another application. Reviews expire after five minutes.

The runtime verifies the original successful invitation receipt, immutable Keycloak user UUID, original app/invitation/creation-operation attributes, owned published realm and client, current role policy and user metadata. It rejects missing or conflicting evidence, identity-provider links, user-storage federation and existing offline sessions. No email search selects the mutation target. Only the exact user’s `enabled` field is set false, followed by its scoped logout endpoint. User records, credentials, role definitions, invitation history and application business data remain intact. There is no account deletion, automatic re-enablement or new grant.

The runtime reads the owned realm’s normal and implicit access-token lifetimes and bounded complete client inventory, including client lifetime overrides. The reviewed artifact binds this configuration and the measured conservative limit; malformed, missing, session-derived (`-1`) or over-one-day lifetimes make this workflow unavailable. A changed user, release, policy or token configuration requires a fresh review. The UI reports the measured seconds instead of assuming a five-minute app token lifetime. Previously issued JWTs keep their own expiry; an earlier longer configuration is not attested by the current metadata. This workflow does not add per-request token introspection or promise immediate denial of every already issued token. Keycloak’s [token expiration implementation](https://github.com/keycloak/keycloak/blob/26.8.0/services/src/main/java/org/keycloak/protocol/oidc/TokenManager.java) distinguishes realm, implicit and client settings.

Before any identity mutation, the broker encrypts, synchronizes and reads back the exact approval, operation, original user projection and pending binding. Approval consumption and operation intent are also retained in the control store. A lost response remains pending; refresh performs read-only identity queries and never repeats a PUT, logout POST, password reset or account creation. Confirmation requires the same owned local user to be disabled, its per-user `notBefore` to cover this operation and online sessions to be absent, with other reviewed user attributes and roles unchanged. Keycloak’s [scoped logout implementation](https://github.com/keycloak/keycloak/blob/26.8.0/services/src/main/java/org/keycloak/services/resources/admin/UserResource.java) advances this value and removes online sessions. Offline sessions are deliberately unsupported here. If disablement succeeds but logout does not, a company operator must inspect the original operation; the system does not silently resume writes.

Readback always rechecks current evidence, including previously confirmed operations. Re-enablement, changed metadata or unavailable ownership demotes the displayed confirmation to **Inspection required**. Retained approval/operation records block another dispatch for that user. The UI keeps an uncertain review visible and requires status inspection before preparing another action; only a confirmed pre-mutation rejection permits a fresh review.

Local control HTTP, browser artifact interoperability and TLS fake-Keycloak tests cover owner/MFA/session expiry, exact target and token configuration, competing reviews, replay, federation/offline rejection, retained uncertainty, read-only reconciliation and unchanged records. These tests exercise the protocol implementation with synthetic responses. Real Keycloak disable/login/refresh behavior, Linux fsync failure paths and visual customer acceptance still require separate native qualification; no real user was changed by this implementation work.
