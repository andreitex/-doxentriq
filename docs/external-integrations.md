# External integration protocol and Stripe ingress

The Stripe webhook verifier, metadata inbox, protected endpoint enrollment and HTTP ingress are implemented and locally tested. There is no Stripe API dispatcher, selected-version SDK qualification, payment processing, or production connector qualification yet. The integration research catalog continues to report Stripe runtime access as unavailable. Endpoint enrollment authorizes only receipt of verified metadata; connection registration does not create an active endpoint or outbound execution authority. Internet reachability and reverse-proxy TLS routing are not qualified by these local tests.

`verifyStripeWebhook` handles API v1 snapshot events using Stripe's [documented manual signature protocol](https://docs.stripe.com/webhooks#verify-manually). It requires the original bounded request bytes, SHA-256 HMAC with an active endpoint secret, a five-minute timestamp window, and an explicit account, live/test mode and event-type scope. Two active secrets support rotation. Organization/thin events are rejected. Errors omit payloads and credentials; the returned metadata contains no document/customer payload. The narrow verifier adds no dependency. A future full API adapter still needs a justified choice and qualification of the maintained official SDK or a custom implementation; manual verification is not evidence that custom code is safer.

`recordStripeWebhook` commits verified metadata through the platform store before the HTTP ingress can acknowledge delivery. App and connection access, expiry and withdrawal are checked inside the transaction. Event identity is bound to the app, connection and Stripe event ID; concurrent deliveries persist once. Conflicting bytes for a retained event ID require investigation. The helper does not infer ordering, perform fulfillment, or deduplicate separate event IDs for the same object: a business handler must bind its effects to the relevant business operation. Raw business payloads and webhook secrets are omitted from the journal. Metadata remains on the installation's encrypted storage and MySQL encryption boundary.

The permanent local owner with MFA supplies one or two endpoint signing secrets through the protected Stripe setup form, chooses the application, account scope, test/live mode and event allowlist, then reviews the exact endpoint before approving it. The setup records bind the installation's configured HTTPS origin, app, connection registry version, snapshot payload format, event scope, endpoint-specific keyed secret binding and encrypted-envelope hash. Signing secrets are encrypted with AES-GCM under the installation key and endpoint-specific authenticated context; setup and inspection responses never return them. A five-minute single-use owner approval activates the endpoint. `needs_credentials` registry entries can enroll signing-only ingress without unrelated API credentials; their generic status and outbound permissions are unchanged. The default internal inbox and all external-effect dispatch fences still require a configured registry. The signing-only exception requires the protected ingress's exact transaction-local authorization check.

Protected enrollment and inspection use these routes:

| Method and route | Purpose |
| --- | --- |
| `POST /api/v1/connections/:connectionId/stripe/webhook-reviews` | Submit app, scoped events and protected signing secrets; return a pending endpoint and exact review. |
| `POST /api/v1/stripe/webhook-reviews/:approvalId/approve` | Consume the exact current owner review and activate or withdraw its endpoint. |
| `GET /api/v1/connections/:connectionId/stripe/webhooks?appId=:appId&cursor=:endpointId` | Inspect at most 100 saved endpoint policies and statuses without credentials; omit the cursor for the first page and use the returned `nextCursor` for the next page. |
| `POST /api/v1/stripe/webhooks/:endpointId/withdrawal-review` | Prepare withdrawal of the exact active endpoint, including its original activation approval. |

History pages use ascending creation time and endpoint ID. A cursor must identify an existing endpoint in the exact app and connection; `nextCursor: null` completes that inspection. Refresh from the first page to include newly enrolled endpoints. Inspection and withdrawal retain the approved canonical HTTPS URL even if the current administration origin changes. Activation and accepted deliveries still require the current independently configured origin. Withdrawal validates the saved policy and consumed activation approval without granting delivery at a replacement origin.

`POST /webhooks/stripe/:endpointId` receives the original JSON bytes through an isolated buffer parser with a 1 MiB limit and a 60-request-per-minute limit per source IP. It admits only the exact configured Host and canonical saved path, a single signature and media-type header, no query, body compression, browser Origin or cookie, and the reviewed signing scope. Forwarded host headers grant no authority; Fastify keeps `trustProxy: false`. The owner approval, endpoint row/path identity, complete registry version, encrypted envelope and scope are revalidated inside the inbox transaction after signature verification. Only a committed inbox event or exact retained duplicate receives `200 {received:true}`. Failed persistence, malformed delivery and unavailable or changed scope receive a fixed failure response without payload, signature or arbitrary exception text. The administration SPA cannot acknowledge unknown webhook paths with an HTML `200`.

Withdrawal permanently blocks that endpoint ID, retaining its policy, approval, encrypted credentials and prior inbox metadata. It remains available to the owner even after the app is archived or the generic registry expires or is disabled. Rotation or re-enrollment requires a new immutable endpoint and review; it does not rewrite an approved scope. Withdrawal neither removes the provider's endpoint registration nor reverses an external payment. The metadata-only inbox is not a business-event processor or a fulfillment outbox.

`beginExternalEffect` commits one dispatch token for an app, connection and operation ID before a qualified adapter sends a single external request. The request hash and capability cannot change under that ID. Duplicate queue delivery and a process restart return the retained operation without another dispatch permit. A timeout, network interruption or indeterminate response must be settled as `unknown`; retained dispatched/unknown operations have no automatic reclaim, expiry or retry path. Known outcomes require a normalized receipt hash. The helper does not authorize a provider call or verify a receipt itself; those remain responsibilities of the protected, qualified adapter.

For Stripe POST operations, the future adapter must also retain and reuse the exact provider idempotency key and parameters. Stripe can expire keys after at least 24 hours, so local retained operation state must remain authoritative beyond provider retention. A `500` may have side effects and cannot justify a new key. Reconciliation must inspect the original provider object/request and verified webhook evidence; it must not make a second payment merely because a response was lost. See Stripe's [idempotency reference](https://docs.stripe.com/api/idempotent_requests) and [error handling guidance](https://docs.stripe.com/error-low-level).

Remaining acceptance includes an isolated pinned outbound connector runtime, actual internet ingress and exact Caddy/TLS/Host routing with request deadlines, provider-side endpoint/secret/account qualification, provider API consent and restricted keys, normalized provider receipt validation, business-event processing with its own durable outbox, explicit reconciliation, security scans, and live Stripe sandbox tests. No operational Caddy mapping was added in this slice. The JSON development store tests demonstrate serialized state transitions and restart readability, not power-loss durability; production crash recovery requires live MySQL acceptance. The manual snapshot-event protocol does not establish SDK or API v2/thin-event support.

Code rollback must preserve these journal records. Restoring an older platform database can omit external actions performed after its recovery point; those actions cannot be undone by restoration. A recovery workflow must keep provider execution blocked until its independently retained action history and provider state have been reconciled. That complete recovery control is not implemented by these helpers.
