# Identity, account recovery and directory groups

The platform has exactly one permanent local owner, identified by its fixed Keycloak UUID. Additional platform administrators require Microsoft or Google SSO and verified MFA. Generated applications use separate owned realms, app-scoped local accounts and exact client permission roles. Platform owner status does not grant app permissions. Applications can be explicitly public; an anonymous portal lists only verified public published applications.

Applications can use local accounts without Microsoft or Google. See
[local DMS account setup](dms-local-accounts.md) for the reviewed role and
invitation flow. Private invitations preserve an unverified email claim;
they do not require an unconfigured email service or open self-registration.

Accepted invitation accounts support separately reviewed [individual local-account disablement](app-account-offboarding.md). The action preserves records and data, verifies the configured token lifetime, and keeps uncertain outcomes pending for read-only confirmation; it does not delete users or grant access.

## Owner recovery codes

`scripts/identity.py` constructs the reviewed local-owner flow: required password authentication, then an enrolled TOTP or one recovery code. It preserves the separate mandatory SSO OTP flow and existing client/role grants. Initial owner enrollment requires a password change, TOTP enrollment and saving recovery codes. Enrollment itself must not produce a completed MFA claim: sign in again after setup. Recovery completion is marked `mfa`; it is never mislabeled `otp`. The control application's signature, issuer, audience, exact owner UUID and MFA checks remain unchanged.

Providing a required-action list in a Keycloak import replaces the default list. The helper explicitly retains enabled password-change and TOTP providers as well as the recovery provider; merely attaching their names to a user is insufficient. Unit tests refuse additional owners, federation, registration, disabled enrollment providers and authentication-policy drift.

Keycloak supports twelve sequential, one-use recovery codes and requests the next code in order. Store them offline or in an independent password manager; never paste codes, passwords or TOTP secrets into the AutoSoft chat. The owner can regenerate codes through Keycloak's account console. [Keycloak's recovery-code guidance](https://www.keycloak.org/2025/10/recovery-codes) describes enrollment, ordered consumption and regeneration. Its [26.8.0 AMR implementation](https://raw.githubusercontent.com/keycloak/keycloak/26.8.0/services/src/main/java/org/keycloak/protocol/oidc/utils/AmrUtils.java) derives references from completed, unexpired authenticator executions.

Fresh installer imports enable this qualified flow. Existing realms are not silently migrated; changing a deployed authentication policy requires company review and the same real protocol qualification. The fixture `scripts/test-identity-login.py` tests the installer's generated realm with the exact verified Keycloak 26.8.0 image, synthetic accounts/TLS, an isolated internal network and encrypted test storage. It exercises enrollment, actual PKCE exchanges, signed TOTP/recovery claims, used-code rejection and the real host recovery helper. The sanitized protocol report (private installation record; not distributed) binds the tested source hashes and image digest. Its H2 database is only a disposable protocol test; it does not qualify production persistence, provider consent, browser appearance or the full installation. Never enable recovery by trusting an account attribute, granting a role, inventing an AMR claim, or weakening MFA acceptance.

Audited host-root recovery remains a separate last resort. It verifies the exact permanent non-federated owner, rotates the temporary password, invalidates sessions and forces re-enrollment. With the recovery flow, resetting MFA invalidates recovery credentials as well as TOTP before requiring new codes. Such recovery changes no application role, SSO group grant or business data. Keycloak 26.8 masks universal AMR reference values in its administrative API; the helper checks exact flow/config aliases and mandatory executions, but does not treat a mask as attestation of the underlying value or change those references. Upgrade or authentication-policy changes require repeating the real signed-token protocol qualification. Already issued access tokens can remain valid until their five-minute expiry; session refresh is revoked immediately.

## Microsoft and Google group mappings

Group mappings begin as approved drafts. They grant no group-derived permissions until the permanent owner with MFA separately approves and activates the exact directory scope. The protected resolver and Access controls are implemented; live customer qualification remains required. The app realm's local subject and an email address cannot substitute for verified immutable upstream identity. See [directory authorization](directory-authorization.md) for the implemented endpoints, consent, credential forms, approval boundaries and revocation lifetime.

Microsoft identity binds the configured tenant UUID to signed native `tid` and `oid` claims. The implemented adapter independently verifies the credential's organization and enabled user, then reads complete bounded `/users/{oid}/transitiveMemberOf` pagination using the fixed Graph authority. It accepts only approved immutable group IDs and never follows token-provided overage URLs. Current dedicated application consent is `Organization.Read.All` and `User.Read.All`; hidden-membership groups remain unsupported. [Microsoft's ID-token claims reference](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference) and [transitive membership API](https://learn.microsoft.com/en-us/graph/api/user-list-transitivememberof?view=graph-rest-1.0) describe the external contracts.

For Google, verify issuer, immutable `sub` and the signed Workspace `hd` claim; the login domain hint and email suffix are insufficient authorization evidence. Ordinary `openid profile email` sign-in consent does not authorize directory access. [Google's OpenID Connect guidance](https://developers.google.com/identity/openid-connect/openid-connect) documents identity validation. A protected, separately consented Directory connection must establish the exact customer and immutable Directory user ID, rejecting suspended/deleted or foreign-customer users. Use unique user/group IDs with `members.hasMember` and the read-only membership scope. Its nested membership support is restricted to the same domain; unsupported nesting must remain unavailable, rather than guessing membership. [Google's membership API](https://developers.google.com/workspace/admin/directory/reference/rest/v1/members/hasMember) and [user lookup](https://developers.google.com/workspace/admin/directory/reference/rest/v1/users/get) define the supported calls; [Workspace credential guidance](https://developers.google.com/workspace/guides/create-credentials) covers separately consented directory access.

The broker-owned resolver uses exact tenant/customer bindings, verified HTTPS, bounded requests, denied redirects and encrypted per-user membership evidence. Every backend authorization binds the app, approved policy, protected connection and credential version, native federation chain and short evidence lifetime. Missing consent, incomplete results, expiry or provider outages deny directory-enforced access. Group membership supplies dynamic app permissions; it does not create platform administrators or persistent group-derived Keycloak assignments. Code rollback leaves access policy separate.

No live Microsoft/Google customer directory proof is supplied. Synthetic tests exercise the resolver, freshness, revocation and protected UI, but do not qualify real customer SSO, native subject mapping, provider consent or directory membership. Customer activation remains unavailable until the exact protected setup and independent consent checks succeed.
