# Captured company startup code

The [captured loader](../scripts/company_captured_loader.py) composes operational code from authenticated, held source bytes. A separately authenticated company package supplies the verifier, installer-parent and source-guard captures, the independent operational catalog and signing-key fingerprint. Candidate release rows cannot establish that initial trust.

The loader validates all fifteen operational members before compiling its first operational module. It reuses the original verifier and installer-parent modules, then compiles the other thirteen members with explicit dependency references. Seven existing modules accept a closed, immutable dependency map; absent maps preserve their existing loaders, while malformed supplied maps fail without falling back. There is no source rewriting or sibling import during this composition.

The company entry, authenticated source and complete physical source guard remain live throughout use. Public constructors do not issue capabilities. Source drift, replaced module identities and caught validation failures expire the affected capability. Registration cleanup removes only the exact owned module objects; uncertain references remain retained. The synchronous `call` boundary checks before and after execution. A returned context or deferred operation still requires its caller to retain every enclosing context.

The [separate full-entry module](../deploy/installer/company_full_entry.py) adds six bounded canonical Base64 package captures. All six must match independently authenticated package pins before any code executes. It preserves the loader's original verifier, parent and guard, while capturing the read-only backend and foundation materializer separately. A failed live entry also revokes its exact owned loader origin. Backend or materializer uncertainty remains attached to its original module and cannot be discarded by replacing a module variable.

The existing foundation entry is unchanged. This composition API grants no host operations or full installation authority; full activation remains denied. Its caller must separately verify backend release after source-guard closure and before acknowledging an outer installer stage. Company package provenance, native signatures, Linux capacity, storage placement and the full worker remain separate acceptance obligations.

The loader verification (private installation record; not distributed) records 23 focused controls and nine separate affected legacy suites containing 224 passes, all without skips. Root and independent review verified complete source inverses, 100 preserved definitions and 96 stable evidence inputs. The initial fixture error remains preserved. These 247 distinct controls ran in separate invocations using injected storage and crypto interfaces.

The full-entry verification (private installation record; not distributed) records 20 focused injected passes without skips, complete draft inverses and 52 stable root-reviewed inputs. Its earlier 18-pass run remains historical and is not added to the final count. Neither record establishes native startup or production readiness.

The [stored-startup binding](../deploy/installer/company_stored_startup.py) now holds four exact Store/Source journals and verifies their two prior confirmations through the original installer-parent module. The installation request, release, archive, source inventory, storage reference and original stage action/outcome hashes must all agree before operational composition. Its separately authenticated company caller supplies the original full entry, issued source, physical guard and explicit backend. Constructor forgeries, stale confirmations, replaced files, unexpected children and uncertain closes deny further use.

The stored-startup verification (private installation record; not distributed) records 23 focused injected passes without skips and 45 stable root-reviewed inputs, with complete source/test inverses. The initial 20 passes plus one fixture error remain historical. This API can invoke the original startup verifier only with explicit trusted adapters; it cannot initialize the runtime pair or start services. The company caller must close every outer context and verify backend release before acknowledging a stage. Native positive startup inspection and full activation remain pending.

Fresh installations have an explicit `FullEntry.fresh_installation_modules` route because physical source does not yet exist when its signed creation code must be composed. It checks all fifteen independent catalog rows before executing operational code and keeps one original verifier/parent/bootstrap/store/source assembly. This grants no storage or stage authority. After source creation, `bind_source_guard` binds the genuine physical guard once to those same bytes without recompiling; the guard must then outlive the assembly. Retained and reboot callers keep the existing physically guarded route.

The fresh assembly review (private installation record; not distributed) records 24 new controls and separate unchanged 23/20/23 regression suites, with 90 passes and no skips. The first fixture failures remain retained. The actual full worker, package and native storage adapters still require integration and acceptance.

The materializer now has a separate `materialized_platform_foundation` route for a genuine schema4 source issued by the same original verifier. It captures the fixed 44 host files, the separately declared signed status checker, ten templates, six configuration records and three provenance records, rechecking signed hashes and logical modes before any output effect. Its private temporary adapter invokes original verifier issuance checks throughout materialization and expires on failure or closure. An explicit file backend is required; the existing schema3 route and 44-file catalog remain unchanged.

This 64-file projection excludes the archive and cannot be reauthenticated as a complete schema4 bundle. The caller must retain the original held source and separate Store/archive context and avoid the legacy schema3-only complete-deployment verifier. Earlier local verification (private installation record; not distributed) records twelve new controls plus 37 unchanged regressions for the earlier projection. The status extension passed 113 Linux component cases, including two copied maintenance-command cases and signed diagnostic-row rejection, without skips. Native backend provenance, actual full worker invocation and full installation remain pending.

Stored startup can now borrow an existing fresh assembly through `assembly(fresh_assembly=original_assembly)` or `inspect_initialized(inputs=trusted_inputs, fresh_assembly=original_assembly)`. It requires private issuance by the original loader, the same entry origin and authenticated source, and the same live physical guard already bound to that assembly. The bootstrap, Store and Source modules retain their identities; startup neither recompiles them nor closes the caller's assembly. The caller keeps both assembly and guard live through startup closure. The retained/reboot default still composes its own physically guarded modules.
