# Company artifact retention

The local artifact-store checkpoint (private installation record; not distributed) verifies a fresh standalone source API with 39 passing injected controls, independent review and 31 stable evidence inputs. It does not authorize native installation or startup.

`company_platform_store.py` receives a genuine live complete-source capability, the original held installer parent and the exact live encrypted-storage context. It preserves the original archive, six signed configurations and three provenance files byte for byte under `company/platform-releases/<release SHA256>`. The customer repository remains separate.

The existing root-owned parent must be empty. An exclusive release directory is created before its durable intent; the intent is synced and checked before any artifact bytes are written. Twelve exact files include that intent and the verification record. Files finish with mode `0400`, and the release directory becomes `0500` after its final record is written. Held identities, bytes and inventories are checked again before all owned handles close. Partial output and uncertain closes block reuse; the API never adopts or removes them.

The archive limit is 32 MiB, total artifact bytes are limited to 39 MiB, and each journal record is limited to 64 KiB. The 128-record and 600-second limits are source policies. A native adapter must separately reserve descriptors and disk allocations, supervise kernel operations and qualify performance before any effect. Existing VM capacity does not prove those reservations.

The shared installation-session checkpoint (private installation record; not distributed) subsequently passed 18 new composition controls plus separate runs of the unchanged 39 artifact-store and 51 repository-initializer controls. Independent review and root readback verified 61 stable inputs and the complete source and fixture changes. The optional explicit `installation_request_sha256` now binds both stages to the same immutable installation request; their distinct action hashes still cover their individual requests and captured module bytes. Malformed or mismatched bindings and extension of a completed foundation session are refused. Omission preserves the earlier standalone request format.

These 108 distinct passes come from three separate injected suites, with earlier failures and timeouts retained as historical evidence. They do not establish complete installer assembly or native performance. Stage acknowledgement still requires known closure of the outer source, parent and storage contexts.

Retaining signed inputs does not materialize the full protected execution tree, authenticate its persisted physical files after reboot, qualify the loader, initialize the runtime pair or establish security eligibility. Those controls remain separate prerequisites for full installation.
