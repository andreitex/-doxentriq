# Installation and maintenance

Install one customer per VM. Minimum resources are 4 vCPU and 16 GiB RAM; the recommended production allocation is 8 vCPU and 32 GiB RAM. Reserve sufficient capacity for the preallocated encrypted volume, retained images/releases, workspaces, documents, telemetry and recovery points. Initially the acceptance matrix is amd64 Debian 12/13 and Rocky Linux 9/10.

The company must distribute a reviewed signed release, its public-key trust fingerprint, immutable image lock, runtime manifest and qualified model catalog. Run the installer from a reviewed checkout as root. It installs required host packages and checks existing state. It formats only a newly created LUKS backing file and refuses overwrite or automatic filesystem conversion. Do not bypass the encrypted-storage guard when troubleshooting Docker startup.

DNS must resolve the administration URL, the apps portal, the identity hostname, and application/preview subdomains to the VM. DNS certificate modes are Route53, Google Cloud DNS and cPanel/WHM. Private-CA mode requires installing the exported public CA into client trust stores; never export the CA private key to ordinary users. Provider credentials enter protected setup forms/files and must not be pasted into chat.

On a fresh installation the owner must change the generated initial password, enroll TOTP and save the one-use recovery codes separately from the VM. Enrollment itself does not attest MFA: use the displayed fresh sign-in link and authenticate with the password plus TOTP or the requested recovery code before entering administration. Audited host MFA recovery revokes both enrolled methods and requires new enrollment; already issued access tokens can remain valid until their five-minute expiry. See [identity guidance](identity.md). SSO identity groups and API consent are separate configuration: a Google login does not grant Directory API access; Microsoft overage handling requires actual authorized group resolution. Missing group evidence must deny permissions.

Use the installed `autosoft` maintenance CLI to inspect status, run security checks, create backups, validate restoration, renew certificates and perform audited owner recovery. Review available subcommands before changing a host. Package updates/reboots and destructive restoration require a concrete impact assessment and explicit approval. Ordinary code rollback preserves current documents and database contents.

Backups are encrypted; the initial nightly implementation is a cold checkpoint with a service outage. It stops managed app writers before database/document capture and restarts them afterward. Isolated MySQL restoration verifies archived hashes and table integrity. It does not yet prove full application/broker/cache recovery and cannot authorize destructive migrations. Export the backup key and encrypted-volume recovery information independently. Test off-VM restore before relying on it.

Before stopping a container, maintenance durably records its immutable ID, configuration/storage digest and original lifecycle state in encrypted `backups/quiescence`. A pending journal blocks both new nightly and incremental backups. After an interrupted process, root can inspect it with `autosoft backup-recovery-status`, then explicitly run `autosoft backup-recovery-resume` to resume exact originals whose clean stopped state was recorded. Both commands hold the maintenance lock. Inspection of missing journal state creates no recovery files. Recovery never restarts an unrecorded container, retries an uncertain start, or starts an original whose ownership, configuration, storage or recorded stopped state changed. It continues reconciling unaffected originals and retains uncertainty for company review. A missing stop/start confirmation can require manual reviewed reconciliation even when the container appears stopped/running. Never remove an active pointer to bypass that review. Resumption reports `backupVerified: false`; partial archives and failed checkpoint evidence remain retained, and no backup/restore success follows from restarting services. Local injected tests cover interruption and storage faults; native Linux filesystem durability and interrupted host lifecycle still require acceptance. The journal admits at most 256 original containers and retains up to 4,096 operations before requesting company retention review (about 42 days at the default 15-minute incremental schedule). Completed history is not automatically pruned; active and uncertain evidence is never pruned.

Docker and host diagnostic logs use the persistent journal on encrypted storage, with daily rotation/vacuum and a seven-day retention policy. Loki provides searchable redacted diagnostics. Release/approval evidence has separate retention; log pruning does not prune release artifacts or business data. Actual seven-day retention and redaction under load still require acceptance testing.

Incremental archival runs every 15 minutes and briefly stops generated application writers and provisioning workers to coordinate document hashes, changed files, deletion records and closed database logs. It can interrupt requests. Nightly cold checkpoints stop all platform/application containers. This implementation makes no zero-downtime backup claim. Complete platform recovery and production data replacement remain unavailable; isolated MySQL/document restoration through an archived incremental boundary has passed on synthetic VM data.

One authenticated preview is current per application. Starting another verification invalidates the preceding preview and its pending publication approval. Published release history remains available for independently checked rollback. Preview access uses a short-lived ticket bound to the exact candidate and current MFA administrator session.

The broker checks application and preview TLS leaves immediately and hourly, renews within 30 days, verifies the exact managed container and served certificate, and restores the prior pair when renewed health fails. Renewed secret files retain application UID 10001 and mode 0400. Separate signing-key checks run immediately and every five minutes against the owned realm and exact HTTPS issuer. The app receives public verification keys with an issuer/app/resource-bound receipt valid for at most one hour. Application authentication must check that receipt on each request; the DMS template does so and reloads keys dynamically. The broker stops only the exact managed container when its keys are stale and records the stop before attempting recovery. It never restarts an app stopped by its administrator. This periodic stop is a backstop and may be delayed by an active app operation; it does not replace per-request freshness enforcement.

Nightly archives now anchor subsequent incrementals to the exact checkpoint and parent manifest hashes. Closed binlog numbers must be contiguous, and every document change and deletion must match the complete inventory. Retention keeps the ancestors required by the last 30 days of recovery points; those ancestors can be older than 30 days. Unknown legacy or incomplete archives are retained for company review. A weekly timer tests restoration of the latest nightly MySQL copy without changing production.

To rehearse a specific archived MySQL/document boundary, create a root-protected JSON request with `schemaVersion: 1`, `baseArchive` containing the nightly `.tar.gpg` path, and `incrementalArchives` containing the exact ordered delta paths. Run `sudo autosoft restore-chain-verify /path/request.json`. It verifies encrypted archives, complete file hashes, parent bindings, contiguous logs and changed/deleted documents, then replays the logs into a separate network-isolated MySQL container and checks every table. The installation must include a scan-qualified, signed, immutable `mysql_recovery` company image: MySQL's minimal server image does not contain the required binlog and table-check clients. Native encrypted logs are served through the restored MySQL keyring and replayed through one TLS session as described in the [MySQL recovery guidance](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery-binlog.html). A separate restricted tools container joins only that clone's isolated network namespace and validates server identity against the installation CA. The synthetic Rocky fixture restored the exact recorded rows and document additions, changes and deletions; machine-readable evidence (private installation record; not distributed) binds its sources and unapproved test image. This command never switches production data and continues to report complete platform restoration as unavailable until broker, cache and application recovery have also been demonstrated.

The application portal lists only published applications whose independently verified access policy is public. Private app login links are shared directly; the portal does not reuse administration cookies or expose a private application directory.

Publishing an improvement can optionally authorize automatic recovery to one exact previous release. The administrator reviews both artifact hashes, the previous version, current schema and the grant expiry. Three measured health failures are required; unavailable infrastructure clears the failure sequence. The broker rechecks current routing, schema, approval history and source/image security before recovery. The grant permits one attempt within 30 days, preserves business data and cannot approve an emergency vulnerable rollback or data restoration. Ambiguous outcomes remain pending until the runtime receipt is reconciled.

The platform pauses when model budgets, credential expiry, scan feed freshness, unavailable verification, stale approvals, incompatible schemas or recovery evidence prevent safe progress. Resolve the reported condition and resume the persisted request; browser disconnects do not cancel work.

gVisor runtimes receive only independently inspected private service and connector addresses while keeping TLS host identity verification. Restarting a container does not update these address mappings. During an approved publication or rollback the broker can recreate a stopped, independently proven inactive container with current addresses, preserving every data mount. Running or ambiguously routed containers are preserved and require reviewed company recovery. Preview replacement validates the exact previous image and source receipt, removes only that owned container and retains application data; failed verification evidence never becomes release approval.

Publication records the previous runtime's immutable container ID before handover. Failed candidates must be confirmed stopped before the previous worker resumes. If a routing response is lost, fallback reads the actual route and confirms the restored route independently. Interrupted publication cannot become completed until the captured previous runtime's retirement is confirmed; a replacement, changed source or unavailable inspection leaves the operation pending for company reconciliation. These controls preserve storage and do not retry external payments, invoices or emails.
