# Held company source

The source checkpoint (private installation record; not distributed) records 36 focused passing controls without skips, independent review and root readback of 29 stable inputs. The first 33-control run remains historical and is not added to the current count. A missing-field assumption in the first inert root reader was corrected before either acceptance receipt was written; application source and tests were unchanged.

`company_source_guard.hold_authenticated_company_source` requires the original verifier module, its genuine live issued source, an exact canonical stored source root, an expected device and an explicitly trusted read-only backend. It has no default native backend. Before opening target files, it independently checks complete signed rows, byte/count limits, logical modes and the Git tree. The source root must be beneath `company/source-releases/<authenticated release hash>/source`.

The guard holds every source file, directory and ancestor. It compares fixed path and descriptor identities across all nine fields, requires root ownership and protected ancestors, and enforces physical file permissions `0400` and source/release directory permissions `0500`. It verifies exact bounded directory inventories and every file's bytes, including empty files and corruption with unchanged metadata. The expected device constrains placement; it does not establish encryption. Sibling journal names are checked, while their bytes, prior-stage authorization and encrypted storage remain outer responsibilities.

Only the context factory issues an accepted guard. Immutable data getters and rechecks validate the complete tree again. `require_company_source_guard` additionally matches the original verifier and source objects before any recheck. Caught failures expire the guard; constructor lookalikes, wrong identities and expired values cannot perform checks as an issued capability. Close attempts follow expiration. Malformed or duplicate returned handles, false closes and exceptions retain exact uncertain references, deny new work and are never blindly closed, adopted or retried.

The limits are 2,048 files, 512 source directories, 8 MiB per file, 64 MiB of source and 2,700 held handles. Capture and each full recheck receive a separate 600-second logical budget; original metadata observations never reset. These are policy limits, not reserved native capacity, a kernel IO deadline or a bound for the caller's complete installation. The guard tests use genuine verifier contexts and an explicit RAM target adapter. Native performance, reboot authentication and installation remain separate acceptance work. Captured module composition has its own [local source verification](company-captured-startup.md).

The [explicit Linux/amd64 backend](../scripts/company_source_guard_backend.py) has no default libc instance or native calls on import. It captures trusted OS syscall references and requires an explicitly supplied `LinuxAMD64Getdents64` binding. Directory enumeration opens a separate read-only `.` descriptor beneath the held directory, uses bounded records, and observes that descriptor's single close result. It does not delegate descriptor ownership to an opaque directory iterator. Every enumeration compares the fixed nine metadata fields before and afterward; uncertain close outcomes retain the exact descriptor and release callable.

The caller must invoke `backend.require_released()` after the guard has closed its own descriptors and before acknowledging an outer stage. Guard closure alone cannot establish release of the backend's temporary enumeration descriptor. Known owned closures remain possible during uncertain unwind, while new reads and opens are denied. There is no retry, reset or adoption operation.
