# Checkpoint admission primitive

`scripts/checkpoint_admission.py` is a standalone company component. It is not connected to quota provisioning, maintenance, installation or running services. Its readiness evidence always says `PRIMITIVE_ONLY` and `backupReady: false`. It cannot certify a backup or resolve existing quota, database, registry, daemon or provider operations.

An explicit root initialization creates protected persistent lock files and bound records beneath encrypted data's `quota/checkpoint-admission`. Missing, malformed, linked, replaced or unexplained state fails closed; ordinary construction and startup never initialize it. Production requires Linux root and canonical protected paths. Initialization refuses existing storage, including interrupted initialization evidence.

Directories require root ownership and no group/world write permission; a stable nonzero directory group is permitted. Private records and locks require root:root ownership and mode 0600, and private directories use 0700. Initialization binds quota, base, operations and fences directory identities plus both lock inodes. Native inventories hold a directory descriptor, check path continuity and recheck those bindings. Actually held lock descriptors must match initialization before records can mutate, including when a pathname was restored after a replacement. Native Linux path and descriptor continuity includes change time. Windows fixtures account for path creation time versus descriptor change time only when comparing those two views, retaining complete metadata checks within each view.

`admit()` obtains a shared activity lease and writes an immutable intent before returning. The caller holds it for its entire operation, marks a possible effect before dispatch, and explicitly confirms completion only after its own independent outcome checks. Releasing without a completed terminal record retains unresolved evidence; an exception never automatically creates completion. Process death, elapsed time, cancellation and a lost response do not complete it. Aborting before effects is permitted only without an effect marker.

Completion records are authoritative assertions by the trusted caller; the primitive cannot verify a provider or daemon outcome from its digest. A lost external response must remain unresolved and must never cause a call to `complete()`. A failed record write attempts to retain an uncertainty marker. If valid terminal bytes were already committed and that marker also fails before creation, a later independent read can recognize the terminal assertion. The module does not guarantee that every failed local completion return leaves persistent uncertainty. This dual failure is covered explicitly by an injected control; external outcome reconciliation and native durability qualification remain separate work.

`close()` commits an exact root-bound checkpoint fence while holding the coordinator mutex. It releases that mutex before `readiness()` waits for the exclusive activity lock, allowing existing admitted operations to record completion. Unresolved intents still prevent readiness after their locks disappear. The readiness lease retains exclusive exclusion until explicitly released; it does not reopen automatically.

Lock waits are bounded to at most 50 seconds. Readiness and abort share their supplied wait budget across activity/coordinator locks. New admission never waits for an exclusive activity holder while holding the coordinator. Each lease serializes finish and release calls with a five-second mutex wait; reopening requires that specific descriptor to remain held in exclusive mode. A bounded registry mutex protects descriptor checks against another lease closing its descriptor. These budgets bound lock acquisition, not the whole count-bounded journal traversal or filesystem IO. Native filesystem crash behavior still requires separate Linux qualification.

`abort_and_reopen()` requires the exact current fence, no unresolved work and no previous readiness grant. A live readiness lease may explicitly finish its **primitive scope** and reopen that same fence. These operations retain immutable terminal and transition evidence. Partial or unexplained transition evidence blocks admission, even if an OPEN pointer became visible; the same best-effort error-marker limitation applies when a structurally complete transition survives an ambiguous local return. Neither action represents archive completion, container recovery or approval to resume the whole platform. An interrupted or released readiness grant requires future company reconciliation rather than a blind retry.

Windows controls inject trust, directory-sync, lock and clock adapters while retaining actual exclusive record creation, file fsync, readback and replacement checks. They do not qualify Linux flock, XFS, root ownership, power loss, services or coordinated backup recovery. No native actions are performed by importing the module.
