# Automatic model routing

For each request, the gateway filters the company catalog by configured provider, local qualification and required reasoning tier. It then removes models whose approved context limit cannot contain the conservative input estimate. Only eligible models enter the cost ordering and the maximum of three provider attempts. A request with no eligible context is rejected before a cost reservation or provider call.

The estimate includes UTF-8 prompt, system and schema bytes plus the existing overhead allowance. Input reserves the highest configured ordinary, cached or cache-write rate; output reserves the requested limit capped by the selected model. Confirmed usage must fit these actual reserved input/output limits. A receipt exceeding the input reservation keeps the reservation held and stops fallback, even when the model's catalog context window is larger.

Requests explicitly select standard processing: OpenAI `service_tier: default` and Claude `service_tier: standard_only`. Provider project defaults therefore cannot silently choose a premium tier. Before settlement, the billing response must confirm OpenAI `service_tier: default` or Claude `usage.service_tier: standard`. Missing, malformed or different tiers retain the spending reservation and stop fallback for reconciliation. These request and response fields follow the [OpenAI Responses reference](https://developers.openai.com/api/reference/resources/responses/methods/create) and [Claude service-tier documentation](https://platform.claude.com/docs/en/api/service-tiers).

This policy follows the company evaluation catalog. [Official OpenAI model selection guidance](https://developers.openai.com/api/docs/guides/model-selection) recommends comparing models and reasoning settings on representative tasks and choosing the lightest setting that meets the required quality. The correction adds no model IDs, prices or live qualifications. All configured provider quality, reasoning capabilities and billing behavior still require local evaluations and live acceptance.

Seven synthetic routing controls cover undersized cheap candidates, no eligible context, the three-attempt limit, both provider input accounting formats, exact reserved boundaries and unchanged tier/qualification restrictions. The affected transport and generation tests also pass. No real provider request is made by these controls.

The standard-tier checkpoint (private installation record; not distributed) records 89 passing affected transport, routing, generation, source-selection, core and qualification tests without skips, plus all three TypeScript checks. Two new controls verify explicit request tiers and reservation retention for invalid billing tiers. Independent review found no scoped blocker. The catalog remains unchanged with every model unqualified; this synthetic evidence grants no live provider qualification.
