# Directory group authorization

App group mappings are immutable-ID drafts in the separately approved access policy. Saving a draft never assigns a Keycloak role. The directory implementation evaluates group permissions on every protected backend request and retains encrypted membership evidence for the owner-approved lifetime, default 60 seconds and at most 300 seconds. This is the maximum upstream group-revocation delay. A protected policy, registry, credential version, activation or provider-binding change invalidates access immediately at the next request.

The permanent local platform owner remains separate from app accounts. Local invitations continue to grant their explicitly reviewed app roles. Directory memberships never confer a platform role, create a platform administrator, link identities by email, or write permanent group-derived roles into Keycloak.

## Company setup

The installer provisions a `platform-directory-reader` service account with only `view-users`, `view-realm` and `view-identity-providers`, with token scopes limited to those roles. Its separate protected credential is mounted only in the runtime broker as `KEYCLOAK_DIRECTORY_READER_SECRET_FILE`. The app-realm provisioner is used only to inspect its owned realm. Reader setup checks actual read access to the user-profile and provider APIs without granting mutation rights.

New SSO app realms bind their `company` provider to the exact platform issuer and internal TLS endpoints, with signature validation. Existing realms are not silently upgraded. Missing or changed realm ownership, publication/source identity, company issuer, native provider configuration or protected federation links causes authorization to fail closed.

For each configured upstream provider, run the company image's `scripts/directory-identity-setup.mjs` inside the trusted identity network with the company CA and protected input on stdin. Preview first (`apply` absent or false); review the returned change and artifact hash. Apply only by providing `apply:true` and that exact `expectedHash`. Input contains the protected bootstrap password, provider, immutable tenant/customer ID and `workspaceDomain` (null for Microsoft). Never put credentials into shell arguments, chat or model prompts. The helper changes only the selected platform provider and profile/claim policy. It does not update app realms or user grants.

The helper enforces signature validation, `FORCE` synchronization, disabled unmanaged profile attributes, and admin-only immutable attributes. Microsoft uses the native `oidc-user-attribute-idp-mapper` for `sub`, `oid`, `tid` and `iss`. Google uses its distinct native `google-user-attribute-mapper` for the verified profile's `sub` and `hd`. After setup, existing users must sign in afresh through the upstream provider so those claims are populated. A conflicting mapper requires company repair rather than automatic replacement. A masked client secret is preserved by Keycloak's provider update API.

Company host configuration `APP_DIRECTORY_AUTHORIZATION_ENABLED=1` enables the private control attachment for nonpublic apps. Default is disabled. The broker checks the exact independently owned control container/image/network, supplies its pinned private address and sets only `https://control:3000/api/public/v1/apps/<appId>/directory/authorize`. The control server admits that POST only on its exact private Host, without Origin or query, and still independently requires a signed app token with the exact issuer, audience and `app_id`. Platform cookies are never authorization for this path. Preview authorization requires a published access-policy baseline; an unpublished app fails closed.

## Protected directory connection

Create the credential through the protected Connections form/API and grant it only to the intended app. The registry must contain exactly one official endpoint, one immutable tenant/customer root and the sole capability `directory.groups.read`.

| Provider | Endpoint | Root | Protected credential fields |
| --- | --- | --- | --- |
| Microsoft | `https://graph.microsoft.com/v1.0` | Lowercase tenant UUID | `tenantId`, `clientId`, `clientSecret`, `consentedScopes:["Organization.Read.All","User.Read.All"]` |
| Google Workspace | `https://admin.googleapis.com/admin/directory/v1` | Exact customer ID beginning with `C` | `clientEmail`, RSA `privateKey` (at least 2048 bits), `delegatedSubject`, `consentedScopes` containing the four readonly scopes below |

Google domain-wide delegation must be consented by the Workspace customer administrator for `admin.directory.customer.readonly`, `admin.directory.user.readonly`, `admin.directory.group.readonly` and `admin.directory.group.member.readonly`, each prefixed by `https://www.googleapis.com/auth/`. The delegated subject belongs to the configured hosted domain. Regular Google sign-in consent does not provide Workspace Directory access.

The Microsoft credential uses a tenant-specific client-credentials exchange. The opaque Graph token is not interpreted as an identity token. `/organization` independently confirms the credential's tenant. The signed native identity's `oid` plus `tid` identifies the target user; a pairwise `sub` or email is not substituted for its directory object ID. The resolver reads enabled-user status and the complete bounded `/users/{oid}/transitiveMemberOf` pagination. It never follows an overage URL from a user token. Pagination stays on the exact official user endpoint; incomplete, cyclic, oversized or escaped pages grant no permissions. Hidden-membership groups are unsupported and do not gain access through absent membership evidence.

Google checks the customer's exact ID, gets the user using its protected native numeric subject, requires the returned Directory user ID and customer to match, and rejects suspended/archived users. It completes the customer-scoped group inventory before calling `groups/{immutableGroupId}/hasMember/{immutableUserId}`. Nested membership outside the single configured hosted domain is unsupported. If a real customer's OIDC subject does not resolve to the exact Directory user ID, no email fallback is attempted; company qualification must resolve that identity contract before enabling access.

Protected credentials and provider tokens never enter model context, operation logs or membership records. Connection and evidence envelopes use AES-256-GCM with exact record/reference AAD. Network reads verify TLS, pin an ordinary public DNS address, reject redirects and compressed/oversized responses, and allow only fixed official read endpoints or OAuth token exchanges. A credential declaration does not prove that its upstream account lacks broader rights: consent and least privilege still require customer review. The adapter itself performs no directory mutations.

## App activation and request authorization

The permanent owner with verified MFA requests `POST /api/v1/apps/<appId>/access/directory/approval`, reviews exact group-to-role permission effects and expiry, and approves the returned artifact through `/api/v1/directory/approvals/<approvalId>/approve`. Only those group IDs already present in the exact approved policy may be selected. The five-minute one-use approval binds the policy hash, native identity configuration hash, entire registry hash, encrypted credential version, evidence lifetime and authorization expiry (within 90 days and credential lifetime).

`POST /api/v1/apps/<appId>/access/directory/activate` with the approval ID performs the fixed consent/tenant/customer checks before consuming the review and enabling the exact scope. Provider failures leave it inactive. `POST /api/v1/apps/<appId>/access/directory/<activationId>/disable` immediately revokes that activation and discards its cached evidence. `GET /api/v1/apps/<appId>/access/directory` reports actual protected approval/activation state; availability is not a live-provider health guarantee.

The protected **Access** interface lets the permanent owner with MFA select immutable groups from the saved, approved app policy, review their exact role and permission effects, approve the five-minute artifact, and activate it once. A lost response switches to retained-state inspection. An expired review must be independently read after expiry before preparing another scope; the browser never automatically retries activation. Disabling an exact activation has its own impact confirmation. Eligibility is shown separately from live provider health.

In **Connections**, explicitly choose read-only directory group lookup for Microsoft or Google. The protected form fixes the official endpoint and `directory.groups.read`, collects dedicated credentials and consent acknowledgment, and binds the selected apps and credential expiry. Google accepts a bounded native service-account JSON or RSA PEM file; it extracts only the email and key, ignores supplied URLs, and never renders the key. The credential form does not prove upstream least privilege or consent. Registration, policy drafts and stored credentials alone grant no group permissions. Google's documented key format is described in [its official service-account guide](https://docs.cloud.google.com/iam/docs/keys-create-delete).

The private app authorization POST takes its app access token in `Authorization` and `{target:"api"}` or `{target:"mcp"}`. It verifies the current app signing keys and policy, traces exactly one app-to-company and company-to-native-provider federation link, and validates protected immutable attributes. Local-only, disabled, incompletely enrolled, missing or ambiguous identities cannot obtain group permissions. The response includes only exact app/subject/audience, current approved leaf permissions, policy hash and bounded validity. It does not expose upstream IDs or credentials. Every result is fenced again against policy, activation, registry and ciphertext changes before return.

The reference DMS requests this evidence on each backend operation when the optional URL is configured. Missing, malformed, unavailable, expired, wrong-app, wrong-subject or wrong-audience responses reject the request, including static grants; there is no fallback under configured directory enforcement. Without this optional configuration, existing app-scoped static roles work as before. `/api/session` returns server-verified DMS leaf permissions for display, refreshed by the browser; button visibility never authorizes an operation. MCP tools additionally require the independently signed MCP audience and their read/search token scopes.

## Verification status

Local tests cover real TLS broker reads with synthetic Keycloak representations, app JWT validation, explicit owner reviews, consent schemas, complete Microsoft pagination, Google delegated assertion/customer/group checks, encrypted evidence lifetime, credential changes, asynchronous revocation, DMS permission failures and MCP scopes. No Microsoft/Google tenant, directory consent, customer SSO token or provider credential was available for a live end-to-end qualification. Setup remains fail closed until exact native links/claims and consent checks exist. Synthetic protocol tests are not a claim that a real customer's directory mapping is qualified.
