# Read-only filesystem revocation

The fixed adapter checks its approved access expiry on every request. The broker also checks the current protected source catalog, exact import device/inode, original approved scope and qualified adapter on startup and every sixty seconds. With independently verified container provenance, a withdrawn, expired, changed or unqualified source causes the original adapter container to be stopped. Source files, business data, credentials and approval records are preserved. A stopped adapter is never automatically restarted by this reconciler.

The stop requires the original full Docker ID recorded by the successful adapter probe, encrypted approval and candidate membership, the separately encrypted app resource/network, pinned image, exact read-only mounts and independently inspected private network. A replacement container, writable mount, foreign app/resource, missing record, ambiguous state or unavailable readback is preserved and reported as unavailable. Stop success requires independent readback of that exact original container. The routine never uses name-based deletion, removes volumes, starts an adapter or changes identity grants.

Each pass is bounded to 256 discovered adapters and two minutes; each target has a twenty-second deadline. App publication and revocation share an app lock. Busy app operations defer the check and are reported for the next pass. Unavailable provenance therefore prevents confirmation of revocation; the sixty-second schedule is not an unconditional maximum outage/revocation delay. The report at `runtime/reports/filesystem-revocation-report.json` exposes actual `current`, `stopped` and `unavailable` results. `current` means approval/source evidence remains current; it is not a health or running-state claim.

Changing or disabling a control-plane connection registry entry alone still does not revoke an already mounted running scope. That change blocks new model context, reviews and publications. The separate [explicit withdrawal workflow](connection-revocation.md) lets the permanent owner with MFA review and withdraw one application's original filesystem grant. It retains a permanent encrypted denial record before stopping exact original sidecars; app rollback and provisioning replay cannot regrant that app/connection. Regrant requires a new connection ID. Missing or changed provenance leaves the operation pending, with files, credentials and database records retained.

The catalog watcher evaluates source catalog, inode, expiry and qualification evidence independently of explicit withdrawal records. Only the explicit withdrawal reconciler uses a successfully synchronized withdrawal intent as stop authority. Its status endpoint performs inspection and retains current readback, without stopping containers. The approved per-request expiry remains the final bound when a stop cannot be independently confirmed. Samba also checks request expiry, but neither this watcher nor the new filesystem workflow claims explicit Samba withdrawal for historical receipts lacking original immutable container IDs.

Local tests use protocol fixtures for immutable container discovery, encrypted retained provenance, expired approval checks, changed mounts/images/network/source ownership, busy locks, cancellation, ambiguous inventory and independently confirmed stop outcomes. They are not a claim of a live production Docker revocation test.
