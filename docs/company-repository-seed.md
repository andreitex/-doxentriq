# Authenticated customer-repository initialization

The customer-repository initializer is an explicit company-code API. Full
installation remains disabled. No native filesystem backend, command runner or
loader is selected automatically; the existing mutable `seed_repository` now
raises before executing `rsync`, ownership changes or Git mutations.

The local acceptance record (private installation record; not distributed)
retains 23 source-issuance, 32 schema4 and 51 initializer passes, without skips.
Independent source reviews passed, and root checked 74 stable evidence files
and six complete source inverses. Company gates register 46 modules and 22
fixture selectors. Their five embedded Python blocks and Bash syntax passed;
the complete pipeline and image build were not run. Earlier 13/22 issuance and
37/44/50 initializer runs remain historical and are not added to the latest
106 distinct passes.

## Authority and storage

The caller supplies the genuine live `verify-release.py` capability, validated
through `require_platform_source`. The verifier registers only the exact object
issued by its authenticated context. Copied maps, subclasses and constructor
flags confer no authority. Failed rechecks, expiration or unknown handle
disposal revoke its registration. This control assumes trusted company Python
code; it is not an isolation boundary for hostile code in the same process.

The initializer runs inside the original direct Bash child worker while its
`installer_parent.HeldParent` remains live. The `repository-seed` stage binds the
exact installation, operation, authenticated release/manifest/tree, storage
identity, Git executable pin and captured bootstrap-row hash. A copied startup
observation or another subprocess cannot replace this held parent authority.
The trusted loader must actually execute the corresponding authenticated
bootstrap bytes; recording their hash in an action does not prove code origin.

`SeedStorage` holds the original host/configuration/layout records, installation
UUID, backing file, key and encrypted mount relation. Read-only controls retain
all nine metadata fields. Authorized writes may change backing-file and mapper
timestamps; their first seven fields remain fixed. The recorded repository must
already exist, empty, with UID/GID 10001 and mode 0700. Its five placement fields
remain fixed. The root-private seed journal must be precreated separately.

Fresh admission refuses pending/completed installation state, prior runtime
effects, active or lingering service processes, active timers and any Docker
containers. The original worker must keep startup disabled. These observations
do not establish a global writer fence or authorize use on the existing test VM
with its running services.

## Output and recovery

The plan derives exact Git SHA1 blobs and trees from issued source bytes and
modes. Its `platform` tree must equal the authenticated source tree before an
intent or repository effect. Configuration and signature provenance form a
separate `company-release` tree. The API constructs a parentless seed commit,
branch reference, standard loose objects and a checksum-bound v2 index. It does
not execute mutating Git commands, repository filters or generated scripts.

The root-private operation journal records a durable intent before repository
writes. Output uses exclusive creation through bounded held descriptors.
Only the specifically authorized parent-directory transition is accepted; other
held paths and read-only controls are rechecked. Read-only `cat-file`, index and
HEAD checks compare actual returned bytes against the plan before the terminal
`objects-verified.json` record. Known closure of owned handles is required before
return. The caller must also close its outer source, parent and storage contexts
successfully before acknowledging the installer stage.

An existing, partial or uncertain attempt is preserved and prevents fresh
execution. There is no automatic adoption, replay, reset or cleanup. The separate
read-only confirmation checks the original journal, seed reachability and
unchanged company/platform trees while preserving later app/MCP history and
business data. Customer-writable repository contents never become a trusted
installer execution root.

## Qualification limits

Current controls use an explicitly trusted injected issuer, filesystem and
command adapter. They do not establish real Linux Git parsing, native durability,
mount policy, process supervision, caller loading or throughput. The logical
operation budget is 600 seconds; command output/input, file sizes and record
counts have separate finite bounds.

The 2,048-source-file and 8,192-record policy limits are not native descriptor
admission. Source leaves, loose objects, directories, outer contexts and child
descriptors can exceed a common 1,024-descriptor limit. Native admission must
measure and reserve sufficient capacity before effects. Repeated storage/service
checks also require native performance qualification.

A separate [company artifact-store API](company-artifact-store.md) now retains the
original verified archive, six configurations and three signature-provenance
files through explicitly trusted injected interfaces. The customer repository
does not implement that store. Shared installation-request integration,
native installation,
runtime-pair initialization, actual signed artifacts, security eligibility and
the supported clean-install matrix remain outstanding.
