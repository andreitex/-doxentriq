The company render step prepares a finite runtime directory layout. The runtime parent stays root-owned with mode 0755; the quota storage parent stays root-owned with mode 0700. The broker runs as UID/GID 10001 and receives private mode-0700 children for its reviewed writes, including a `reports` directory for JWKS, TLS renewal and filesystem revocation reports. Its existing dedicated build tmpfs remains UID/GID 10001, mode 0700, nosuid/nodev and bounded to 2 GiB.

Fresh preparation accepts only empty, declared children and empty private storage. It records an immutable intent before changing ownership or permissions, binds the data root and control/runtime directory identities, and verifies exact readback. A confirmed layout permits a read-only rerun while no quota allocation or admission state exists. Partial evidence, unexpected children, populated legacy storage, changed bindings and any existing quota/admission state require separately reviewed company recovery or startup wiring; render never adopts or repairs them. This is not a general rerun after quota initialization.

The broker validates quota responses and supplies the exact host storage path to Docker as an app bind source. It has no direct read/stat traversal of the private storage parent in the reviewed production sources. The privileged quota helper validates storage; an app would receive its own UID10001 leaf at `/data`. Actual daemon binding, Linux DAC, gVisor and SELinux access remain pending native qualification.

Local controls inject Windows ownership, permission, mount and directory-descriptor transport while retaining file identities and durable file readback. They establish `RUNTIME_PLACEMENT_ONLY`, with `backupReady: false`; they do not initialize admission, allocate project IDs, start services or qualify complete backup coordination. The preflight precedes mutable work inside `render`, while earlier installer/foundation/configuration steps retain their existing effects. An acknowledged failure after a valid durable final record can be verified without replay; incomplete records remain retained.

The separate `verify()` operation checks a confirmed layout after initialization. It accepts populated private app storage and existing quota/admission state, reads only the three layout records, and does not inspect or initialize quota/admission state, reopen a fence, change ownership, create directories, or rewrite receipts. `prepare()` retains its previous restrictions and still rejects initialized state.

Permanent data, configuration, layout-control, runtime, private storage and broker-child bindings stay exact. Builds are the sole ephemeral exception: a remounted tmpfs may have a different device/inode from the saved layout, while its persisted UID/GID 10001, mode 0700 and exact typed mount record (target, tmpfs, 2-GiB cap, nosuid/nodev) remain mandatory. During one invocation, read-only noninheritable directory descriptors remain held; current path/descriptor identity, ownership and mode must agree throughout, and both current mount observations must agree. Authorized child contents may change. Unknown mounts, replacement during verification, malformed types, changed permanent bindings and incomplete or changed records fail closed without repair.

This verifier establishes placement only and returns `changed: false` and `backupReady: false`. It grants no installer completion, Gate/allocator readiness, recovery, publication or native permission/mount qualification. It does not freeze application writes or provide a complete backup checkpoint. Local descriptor transport and mount observations are injected controls; native Linux FD, Docker/gVisor and SELinux behavior still require their separate qualification.
