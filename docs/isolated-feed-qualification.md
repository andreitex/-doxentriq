# Isolated Trivy feed qualification

`scripts/qualify-trivy-feed.py` is a separate company validation controller. It does not call global maintenance scanning, activate a cache, initialize quota or backup coordination, update a service, or publish a release. Without `--native` it reports `native_dispatch_disabled` and performs no daemon work. This source slice has only injected local qualification; native Linux/gVisor/Trivy behavior remains unqualified.

Native admission requires an independently reviewed, canonical, root-protected scope with its exact externally supplied SHA256 and length, one fixed fresh `/srv/autosoft/validation/trivy-isolated-scanner-v1-<operationId>` namespace, exact spending-free resource bounds, a current UTC window and `nativeDispatch:true`. The scope pins independently supplied canonical company scanner evidence and feed evidence. An installed image reference is insufficient company approval. There are no default/latest scanner values. Only the reviewed Trivy **0.75.0** contract and fixed `/usr/local/bin/trivy` entrypoint are supported; other versions fail closed.

The company tuple contains `schemaVersion`, `status:company_approved_scanner`, digest-pinned `image`, `version`, `entrypoint`, and the exact independently supplied Docker image-inspection byte hash. This means approval for these isolated probes; `companySecurityEligible` remains false. The feed tuple contains its fixed quarantine `directory`, exact `db`/`metadata` SHA256 and byte pins, and schema2 timestamps. Their canonical bytes must match scope `companyEvidence`/`feedEvidence` pins. These tuples must be prepared and approved independently; this controller does not establish their company provenance. Original feed files and protected ancestors are held with nofollow FDs, hashed before/after, observed throughout, and never chmod/chown/relabelled or copied.

Three sequential containers observe the approved version and scan two text-only Debian12 dpkg inventories. They contain `libcurl4`, source `curl`, at `7.88.1-10` and `7.88.1-10+deb12u4`. The positive report must contain exactly one CVE-2023-38545 advisory with a strict string severity of `MEDIUM`, `HIGH`, or `CRITICAL`, Debian source and that fixed boundary. `LOW`, `UNKNOWN`, missing or malformed severity cannot satisfy this positive fixture. The negative report must positively list the fixed package and exclude that CVE; other findings are permitted. Package release/source-release fields are reconstructed using the reviewed Debian parser contract. A supported scanner report is schema2, `filesystem` `/inventory`, Debian12, positive package inventory and the exact scanner version. This severity-policy correction has injected local controls only; it neither qualifies a fixed package nor authorizes another native probe, feed activation or promotion.

Each container uses runsc, UID10001, no network, no capabilities, no-new-privileges, a read-only root filesystem and original feed bind, and separate 64MiB cache/128MiB temporary tmpfs. The artifact cache is in memory. No credentials, sockets, registry access, image pulls, host namespace, devices or relabel options enter a container. SELinux/AppArmor stay enabled; an access denial is unavailable. Container memory is3GiB with equal memory-swap,2CPU and64PIDs. The overall operation is600seconds, with480active seconds and120seconds reserved for cleanup; each scan gets at most120seconds. There are at most3containers and48daemon calls.

The local host Docker CLI is the only daemon adapter. It uses an explicit local socket/config, clean environment, no shell, bounded output, an owned process group anchored by the unreaped direct child, and bounded termination/reap/close. Native execution requires a sole reaper, the default SIGCHLD policy, a pidfd, and one thread. No poll/wait/communicate consumes the leader before the last numeric group termination. WNOWAIT revalidates child ownership before signalling; after reap only signal0 absence observation is allowed. Lost ownership forbids signalling and latches unknown; failed cleanup preserves exact process/pipe/FD references and denies subsequent commands. Five seconds inside each command timeout are reserved for reap/close. CLI completion is separate from container outcome. Every create has a durable intent. Only an exact64hex ID with independently confirmed immutable inspection profile gives cleanup authority. No cleanup uses a reusable name, label enumeration or broad prune. Unknown create/start/cleanup outcomes stop subsequent probes, preserve pending intent/output and deny qualification. Exact-ID absence and all releases are required. The fresh namespace is never adopted or automatically removed.

Command/result hashes are durably appended to one bounded command journal; capped attached stdout/stderr and fixed stage records are retained separately. This keeps the finite file ceiling40 while retaining up to48command records. Total retained writes are at most16MiB; each stdout is at most2MiB, each stderr64KiB. These are admission/owned-write caps, not an XFS host-quota guarantee. Result retention failures return unavailable. Original feed hashing is streamed, and actual metadata timestamps must match the independently pinned feed tuple. Admission/freshness is rechecked after initial hashing, before new daemon commands and at terminal; expiration still permits bounded cleanup of an already owned exact ID. No bbolt/Trivy default Init runs on the host.

Before journal creation, native admission holds each protected canonical validation-parent FD and checks bounded current mountinfo. The unique longest covering mount must identify `/dev/mapper/autosoft-data`, match the held parent's device and a root-owned block-device measurement. A different, replaced or ambiguous mount denies admission; the controller never mounts or unlocks storage. It measures at least80MiB available before writing, which is not a reservation. The fresh root/once intent and fixtures are created before the initial feed ancestor snapshot, so this known sibling creation does not invalidate the shared validation parent's continuity. A bad feed leaves the exact fresh intent but performs zero daemon calls; no held guard is rebased. Parent/root/fixture directory FDs remain held and checked, writes use their directory descriptors, every newly owned file FD is registered before metadata operations, and all releases are attempted. The final result reopens only the same independently stable directory identities and closes those FDs too. Close failures preserve references and deny success. This checks the fixed mounted encrypted namespace; it does not establish complete storage, runtime or backup readiness. A600second process alarm covers preparation as well as active work and cleanup; future dispatch must independently bound the controller lifetime and must not infer daemon cancellation from controller exit.

CPU120seconds,48FDs,zero core output and16MiB file-size limits apply to the native controller and inherited CLI. The earlier design's256MiB address-space cap is deliberately omitted: a small inherited RLIMIT_AS can prevent the Go Docker CLI's virtual reservations. Controller content sizes, streaming buffers, JSON depth/counts and captured outputs remain bounded, but actual controller RSS has no OS memory limit (`controllerMemoryLimitEnforced:false`). The scanner's3GiB cgroup ceiling is unchanged and independently inspected. No bounded-source test establishes native resource enforcement.

Successful native evidence would prove read-only opening and a specific Debian advisory/version comparison by the exact scanner/feed pair. It would not prove full bbolt integrity, all advisories, application OCI/image/language/Java scans, Rocky host coverage, publisher signatures, global feed readiness, backup readiness, production security or remote cancellation. The original acquisition/public records remain unchanged. Native execution requires a separate accepted scope after SOURCE review.

The Docker identity boundary keeps the approved multi-platform index reference separate from the selected linux/amd64 manifest. The independently hash-bound `image inspect --platform=linux/amd64` bytes must contain a descriptor whose digest equals that selected image Id, whose size is a strict integer from1through4MiB, and whose media type is OCI image-manifest v1 or Docker distribution-manifest v2. Only `digest`, `mediaType`, `size` and optional `platform` are allowed. A missing platform is filled with exactly `architecture:amd64,os:linux`; a present platform must already equal those two fields. Variant, annotations, extra descriptor fields and other platforms are denied. Container inspection must match the exact approved index digest in `Image`, the full approved reference in `Config.Image`, and the exact authenticated selected descriptor in `ImageManifestDescriptor`. That descriptor is included in every immutable profile check through cleanup.

Docker may reorder environment entries. Inspection compares exact bounded, unique `NAME=value` entries by name and value, with no duplicate names, changed values, missing entries or extras. Their order is normalized in the profile; the strictly validated OOM field is normalized as described below, and every other configuration field retains its original binding. The retained first native attempt stopped before any start on these identity checks. This source correction does not grant removal of its unbound created container or replay of its consumed scope. A further native probe needs fresh independently pinned source, transport and authorization.

Docker mount representation: the controller uses `--tmpfs`, whose destination/options map is bound through exact `HostConfig.Tmpfs`. Docker's API represents that map separately from its reported `Mounts` array. The retained created-container observation reports two bind mounts and no tmpfs entries in that array. Inspection therefore requires exactly the two authorized read-only, `rprivate` bind paths and accepts either no reported tmpfs entries or exactly both expected tmpfs destinations. Partial, extra, duplicate and unknown mount entries are denied. The exact `HostConfig.Tmpfs` options remain mandatory in both representations. The full returned `Mounts` array remains in the immutable profile digest; its representation cannot change during one operation.

The new controls exercise these two representations and their rejected variants through injected inspections; the two-bind lifecycle control uses an injected daemon only. They do not remove the retained container, retry cleanup, start a scanner or establish native qualification. Primary references: [Docker tmpfs mounts](https://docs.docker.com/engine/storage/tmpfs/) and [Docker Engine v1.51 API definitions for HostConfig.Tmpfs and MountPoint](https://raw.githubusercontent.com/moby/moby/v28.5.1/api/swagger.yaml).

Docker can clear `OomKillDisable` to `null` when that control is unsupported, including a requested `false`. The existing isolation gate still requires this field to be present and exactly `false` or `null`; `true`, numeric/string values and missing fields remain denied. After that gate, the immutable profile uses a copied `HostConfig` with `OomKillDisable:false`. This equates only the two already admitted representations and leaves the parsed inspection unchanged. Other host configuration, mounts, image identity and configuration drift remain denied. [Docker Engine v28.5.1 resource validation](https://github.com/moby/moby/blob/v28.5.1/daemon/daemon_unix.go).

The seven added controls check both admitted transitions, rejected types and missing fields, input preservation, unrelated drift, and an injected poststart-null lifecycle. They launch no native process or scanner. The separately observed version-only transition does not qualify full scanner behavior, remove a retained fixture, authorize replay or establish production eligibility.
