# Protected migration capture and clone import

The broker now captures an app-scoped database snapshot before calling a candidate verified. This is **capture evidence only**. It does not certify that a migration preserves records or that the previous and candidate application versions work against the new schema. Those functional contracts remain unimplemented. An existing application with unapplied migrations is unavailable for verification and blocked before live DDL during publish, rollback, emergency rollback and automatic recovery.

The signed, private broker POST routes `/v1/migrations/snapshot` and `/v1/migrations/snapshot-status` accept only an app/job/attempt/fence, immutable current base release/artifact/image, source hash and ordered migration-set hash. They accept no credentials, host paths, database names, arbitrary SQL, endpoints or caller-selected limits. The same app lock and retained worker fence apply. The broker independently checks the active release, exact source tree, retained resource identity and hash-derived database/account. Control validates the same immutable base artifact/image and rechecks the worker lease, fence and active release before accepting evidence. Status never recaptures an interrupted transaction.

Capture uses verified MySQL TLS and the protected app account on one connection, UTC session time, repeatable-read isolation and one read-only consistent snapshot. Metadata and the actual migration ledger are read before, inside and after the transaction. Any mismatch, cancellation, unsupported schema, stale context or missing evidence is unavailable. This follows MySQL's [consistent snapshot transaction contract](https://dev.mysql.com/doc/refman/8.4/en/commit.html) and [ordinary consistent SELECT behavior](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html). No `INSERT ... SELECT`, clone, live DDL or preview business-data copy occurs during capture.

Supported capture is limited to InnoDB base tables with an explicit complete primary key, safe ordinary identifier names and supported integer, decimal, binary/blob, character/text, JSON and temporal raw-value types. It rejects views, generated columns, auto-increment columns, foreign keys, triggers, unsupported extras/types and incomplete metadata. The broker preserves measured column type, ordinal, nullability, default, charset/collation and the complete table definition. It compares the actual ledger with protected retained `Applied` metadata; a new candidate cannot silently omit a previously applied migration. It does not repair inconsistent metadata or advance the schema epoch.

MySQL [trigger metadata requires TRIGGER privilege](https://dev.mysql.com/doc/refman/8.4/en/information-schema-triggers-table.html). The ordinary provisioner and generated app credentials do not establish that visibility. Existing-table capture therefore requires a company-configured `MYSQL_SNAPSHOT_AUDITOR_USER` and protected `MYSQL_SNAPSHOT_AUDITOR_PASSWORD_FILE`, on the same fixed verified MySQL endpoint. The code accepts only that authenticated account's USAGE and exact literal app-schema SELECT/TRIGGER grant, without roles or extra scopes/rights. **TRIGGER is not a read-only grant:** it also permits creating/dropping triggers. The trusted capture code executes fixed metadata reads only; it never creates the auditor account, expands its grants or exposes its credentials to generated code. Missing/unqualified auditor configuration keeps capture unavailable. Company configuration and real MySQL protocol qualification remain outstanding.

The fixed limits are 120 seconds, 64 tables, 128 columns/table, 8 primary-key parts, 100,000 total rows, 512 KiB raw values per row, 1 MiB encoded frame and 256 MiB encrypted stream. Each table's row count/maximum raw length is checked inside the same transaction before loading row values. Raw decimal/binary/temporal bytes use driver `parseTime=false`; NULL and empty bytes are distinct. Rows are ordered by the complete primary key and hashed with a request-bound HMAC key derived under a separate domain from the random stream key.

The broker retains an encrypted intent and random stream key before capture. It writes authenticated, sequenced encrypted frames and a final completion frame, synchronizes the file and containing directories and verifies ciphertext hash/authentication on completion/readback. The encrypted runtime root is a trusted deployment prerequisite; Linux file/directory synchronization is required. Private partial streams and intent records remain for inspection on errors. A repeated exact request returns its retained outcome; it never resumes a lost database transaction. No stream, keys, raw rows, database credentials or table definitions enter public receipts, model context, chat, logs or preview mounts.

Receipts explicitly report `captured_only` / `not_run` and `publicationEligible:false`. Genuine genesis reports `no_previous_release` only after independently finding no active release, retained app resources or exact database. The provisioner's own verified TLS identity, supported privilege semantics and SELECT visibility of the app namespace must be proved before a filtered `SCHEMATA` zero can establish absence. An orphaned database is unavailable, not a fresh start. After admission, an existing database never enters the migration writer, including its `CREATE TABLE IF NOT EXISTS` path. Only a genuinely absent app database can run the initial schema creation. Historical artifact hashes remain unchanged when no snapshot field was present; capture does not rewrite old artifacts or delete old data. Historical code-only recovery without capture uses the actual migration ledger and retained applied history; it does not acquire the stricter capture schema limits or claim schema compatibility from the ledger. Captured proof additionally requires the exact encrypted retained stream and current measured schema/object evidence. Status and cached verification perform durable readback without recapturing SQL.

Local synthetic tests verify validation, privacy, limits, unsupported metadata, ledger/context drift and admission without DB mutation. Linux-only tests cover encrypted retention and file/directory synchronization. This source slice has no live MySQL capture, native durability, old/new DB functional compatibility, preservation, restore, deployment or image-qualification acceptance claim. Full migration execution on an existing app remains blocked until a later independently verified preservation and previous/candidate release compatibility contract exists.

## Internal clone importer

The internal importer authenticates the complete retained encrypted stream before issuing any clone SQL. It creates a request-bound separate database through the trusted provisioner, reconstructs only supported typed tables, inserts parameterized values, and independently compares the old columns, primary keys, migration ledger and keyed row digests. It receives no caller-selected database name or SQL. Rejected SQL sessions are closed and cannot be reused by a later attempt.

An exclusive durable pending record precedes clone creation. Interrupted or quarantined imports retain their partial database and evidence; another call cannot replay writes. A completed import is checked through read-only proof. The importer is not exposed by an authenticated API route yet, and a missing status record must never invoke this writer.

The local importer receipt (private installation record; not distributed) binds the source and actual tests. Independent focused runs each passed eighteen top-level tests and seventy-two tests including subcases, with one explicit Linux durability skip. The full Windows Go suite passed 209 top-level tests with six explicit platform skips; vet and Linux cross-compilation passed. These tests used synthetic SQL drivers. No Linux binary or live database import was executed.

Clone reconstruction alone reports `publicationEligible:false`. Candidate migration DDL, current write quiescence, previous/candidate application contracts and schema epoch advancement remain `not_run`. No existing publishing or recovery gate has been relaxed.

A separate internal metadata review derives the proposed clone request from
protected verification and capture records. It authenticates the full stream,
rechecks source, active release, fence and resource bytes, then returns an exact
five-minute artifact hash. It opens no SQL connection and grants no execution
authority. Retained-state inspection is separate: missing state is unavailable,
and pending, quarantined or imported metadata never invokes the writer. Its
local admission receipt (private installation record; not distributed)
records nine top-level tests and forty-eight including subcases in each focused
run, with one explicit Linux path/mode skip. A future endpoint still requires
authenticated owner/MFA approval, durable one-use execution and live readback.
