# Deployment and recovery

Run the reviewed company checkout on a dedicated x86_64 VM running Debian 12/13 or Rocky Linux 9/10. The complete platform requires at least 16 GiB configured RAM and four vCPUs; 32 GiB is recommended. The preflight accepts 15 GiB `MemTotal` to allow up to 1 GiB reserved by kernel/firmware. Docker, containerd, gVisor, encryption, identity, databases, routing and monitoring are installed by the script.

```sh
sudo bash scripts/install.sh
```

The installer collects three HTTPS origins (admin, apps and identity), permanent storage location/capacity and LUKS backing-file location, DNS certificate mode and credentials, SSO credentials, model API keys, qualified company model catalog, spending limits, timezone and optional SMTP/off-VM backup settings. AWS Route53, Google Cloud DNS, WHM/cPanel DNS and installation-CA certificates are supported. The company release signing fingerprint must come from a separate trusted channel.

Only a newly created, preallocated file can be formatted. Existing files, block devices, mapped volumes and data are never silently reformatted. The root-owned pending transaction binds the new LUKS UUID to its backing file before filesystem initialization. Startup checks the expected encrypted mapping, XFS project quota enforcement, encrypted Docker/containerd paths, encrypted persistent journals, bounded build tmpfs and disabled swap. Export `/etc/autosoft/storage.key`, the installation metadata and backup encryption key securely outside the VM: losing those keys prevents recovery. Automatic mount keys protect stored disks; an external KMS/unlock workflow remains a separate operational integration.

## Company release

Platform builds require a fresh `SECURITY_SCAN_NONCE` build argument; `build-company-release.sh` generates it automatically. The full locked public dependency inventory is checked through the fixed npm Bulk Advisory endpoint without sending private project/workspace identities or falling back to a full-tree upload. Production dependency installation depends on that checked stage. This is one security gate; image, source and configuration scans remain required.

`scripts/build-company-release.sh` builds only the reviewed company Dockerfiles, refreshes official supported patch sources, resolves exact image digests, runs application/Go/infrastructure tests and moderate-or-higher dependency audits, scans each concrete company/infrastructure image, and prepares a release manifest. Unknown findings, missing image scan coverage, end-of-life OS images and MEDIUM/HIGH/CRITICAL vulnerabilities block publication.

Required environment inputs are `COMPANY_REGISTRY`, `RELEASE_VERSION`, immutable `GO_IMAGE` (Go 1.27.2), immutable `DOCKER_CLI_IMAGE`, and exact stable Alpine `GIT_VERSION` and `ZLIB_VERSION` values available for that base. The tested remediation candidate used Git `2.54.0-r0` and zlib `1.3.2-r1`; those package versions are explicit company inputs, not a qualification default. Log in to the company registry using the Docker credential helper or a protected Docker config. Signing is a separate operation with an Ed25519 private key outside both the source checkout and output directory:

```sh
bash scripts/build-company-release.sh /protected/releases/version
bash scripts/sign-company-release.sh /protected/releases/version /offline/company-ed25519.pem
```

The runtime image removes only the unused active Buildx/Compose binaries and a verified Compose alias. Core Docker and the CA bundle must keep their original hashes, and the Go build stays unchanged. Package scripts are disabled; all other installed package identities must remain unchanged. A required dependency or CA change therefore stops the build for separate company review. Plugin bytes can still remain in lower parent layers. Every new company image still requires the complete fresh scan, qualification and signing gates; an earlier candidate's scan or capability receipt does not qualify a later source build.

The installer verifies the bundle against an independently supplied public-key fingerprint before using its files. Generated apps are installed, compiled and tested in gVisor without host sockets/secrets. Only controlled dependency downloads use the whitelisted proxy; generated scripts run offline. The packager adds validated artifacts to the exact same approved Node 24/Python 3.13 runtime base used for the build. It never runs a generated Dockerfile or build script. Architecture and native-module ABI therefore match. Persistent app directories use kernel-enforced XFS byte/inode quotas; build workspaces use a 2 GiB tmpfs and artifacts are separately capped by the broker.

## Maintenance

`sudo autosoft status`, `check`, `start`, `stop`, `recover-mount`, `grow TOTAL_GIB`, `security`, `certificates`, `backup`, `restore-verify FILE.gpg` and `owner-recovery` provide host maintenance. Recovery never formats data. Storage can grow but cannot shrink through this CLI. Owner recovery verifies the exact permanent local owner and records a redacted host audit. PASSWORD mode preserves enrolled factors. MFA mode requires an explicit impact acknowledgement, removes only that owner's OTP and recovery-code credentials, invalidates refresh sessions and requires password change, new TOTP and recovery-code enrollment. Previously issued access tokens may survive until their five-minute expiry. Other SSO administrators and app identities are unaffected.

Nightly checkpoints are encrypted locally and retained 30 days. They briefly stop the platform and generated apps for a consistent cold snapshot, then restart previously running containers. Every 15 minutes the trusted maintenance job briefly stops generated document writers and provisioning workers, closes MySQL binlogs and saves changed app documents with a full hash/deletion inventory, native keyring and quota state. Both jobs optionally copy their encrypted archives to a separately mounted off-VM destination and verify SHA256. Local backups cannot survive loss of the VM; external shares, mailboxes and API providers require their own backup policies. Storage capacity must allow retained snapshots, encrypted archives and the nightly temporary archive.

Restore verification checks archive safety, hashes and the exact MySQL image/data/keyring in an isolated container. Complete app/Redis/RabbitMQ recovery and replay to an arbitrary point in time remain **unavailable until exercised and proven**. A successful backup archive alone never authorizes destructive migrations.

Daily scans use refreshed vendor OS/package advisory data and report MEDIUM and higher findings with fixed versions where available. The running kernel is bound to exact distribution package/source and boot-image metadata; ambiguous identity, changing metadata and stale feeds leave coverage unavailable. Unsupported coverage is shown as unavailable: third-party Docker/containerd/gVisor advisories and firmware/SSH/hardening checks still need validated coverage. Daily app checks cover all retained rollback releases through the trusted broker's exact source/independent receipt gate, then current dependency, configuration, secret, static-policy and image checks. Business acceptance evidence remains from the verified immutable build. A failed or missing daily check is unavailable. No remediation silently changes packages or data. SMTP alerts use verified STARTTLS and can fail independently while retaining the admin report.

The trusted maintenance scanner has separate time, output and resource limits, a protected local Docker endpoint, an empty CLI configuration and persistent captured-ID cleanup evidence. Unknown creation, profile drift, timeout or incomplete cleanup preserves the journal and affected scanner inputs for company inspection. Only confirmed cleanup evidence may expire after seven days. Image export now has its own 300-second CLI and file-stage deadlines, 2 GiB archive ceiling, stored OCI layer hash verification and confirmed-only diagnostic retention. The integrated export/scanner/caller suites pass 118 local tests. Native host scanning completed, but image scanning was unavailable and captured-ID recovery remains untested; the new export helper also needs native verification. Other maintenance subprocess gaps remain. These results do not accept the complete daily security workflow.

Container logs are stored in encrypted persistent journald with seven-day retention; a trusted collector redacts known credentials and sends the last seven days to Loki. Prometheus, Grafana, Loki, OTEL, control, broker, packager, databases and generated apps use TLS. Telemetry dashboards require the admin session/MFA. Reports and metrics use separate scoped bearer tokens. The quota helper reports actual host CPU, RAM, disk, uptime and encrypted mount state through an authenticated read-only Unix-socket endpoint.

The apps root serves a separate public catalog and invitation page through only `GET /`, `GET /invite`, `GET /api/public/v1/apps`, `GET /portal-assets/*`, and `POST /api/public/v1/invitations/inspect` or `/accept`. Invitation tokens remain in the URL fragment and protected request body. It lists explicitly public, verified published apps. Its proxy strips incoming cookies and Authorization, preserves the exact host and verifies the control service's TLS certificate. Admin, identity and internal endpoints are unavailable through that host; unpublished wildcard app hosts return 404.
