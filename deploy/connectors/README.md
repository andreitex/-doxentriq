# Read-only Samba connector

The DMS uses the existing `SambaConnector` HTTPS contract. Applications receive an app-scoped registry and bearer token; they never receive the remote username/password, a share mount or a host path. Two company-owned gVisor containers are provisioned per immutable release candidate/connection: a read-only adapter on private app/connector networks, and a sealed TLS relay on private connector/dedicated egress networks. The relay selects one approved literal IPv4 address on port 445 from its immutable configuration. It accepts no destination in an application request.

The adapter requires encrypted SMB3.1.1 and a dedicated server-side read-only account confined to one ordinary share. The approved logical root represents that share. Client read-only operations do not independently establish that the remote account lacks write rights; the company must review and record the server ACLs. Arbitrary subtree isolation, DFS, Kerberos, hidden administrative shares, SMB downgrade and writes are refused. The trusted relay is a network gateway; the current destination restriction is enforced by its code, with no claim of kernel destination firewalling after relay compromise.

`dossier.json` records primary documentation, provenance, licenses, guards and qualification limits. `requirements.lock` pins official PyPI wheels and all five dependencies for CPython 3.13/Linux amd64. The fixed connector Dockerfile runs the unit/protocol policy tests and `pip check`. The company pipeline's `WITH_SAMBA_CONNECTOR=1` additionally builds an isolated synthetic Samba server, performs actual HTTPS/relay/SMB read/list and denial checks, scans both images against a fresh feed and blocks every MEDIUM+ or unknown finding. Only then can it include a signed `connectors.samba.image` private-registry digest and a protocol report hash in the runtime manifest. Omitting this flag keeps the connector unavailable. A missing live test, package feed or scan never produces a passing receipt.

The protected company/owner credential form sends a signed `/v1/connectors/provision` request to the trusted broker. It requires the exact permanent owner subject, verified MFA, an approval less than five minutes old, an expiry within ninety days, the reviewed ACL record SHA256, one app/connection identity and protected account credentials. This prepares encrypted immutable state; it does not start containers or claim connectivity. Changing the scope or credentials requires a new reviewed connection identity. Application verification requires independently stored approval state. During isolated candidate staging, the broker checks a fresh image scan, starts only the fixed company image, validates the actual container isolation/mount/network inventory and performs an actual encrypted share-root listing. Failure blocks the app.

The generated app receives only `/run/app-connectors/connector-registry.json` and `/run/app-connectors/connector-token`. The adapter checks app ID, connection ID, root, capability, token and expiry on every request, even when generated code has skipped its own checks. File reads are capped at 16 MiB and listings at 1000 entries. Logs contain only operation/outcome/timing and follow the existing seven-day encrypted journal policy. Daily app security checks must include the connector image scan hook alongside the generated app image.

The real isolated synthetic rehearsal passed on the supplied Rocky Linux 10.2 VM at 2026-10-10T12:36:58Z, with all ten actual-SDK image tests passing and verified TLS relay, encrypted SMB3.1.1 listing/document/nested reads, app/root/traversal/write/symlink and wrong-token denials. Its source and immutable image bindings are recorded in `../verification/rocky10.2-samba-protocol.json`. The test removed its own three containers and private network. It did not run the company's fresh Medium+ image/security scan or sign/publish an approved release; customer ACL/connectivity, Windows server and Kerberos evidence remain unavailable. The VM memory guard still blocks the full platform.

Each candidate has a separate encrypted ownership index, app-scoped token, read-only `/run/app-connectors` capability mount and sidecar identities. Candidate failure preserves the currently routed release's connector scope. After confirmed publication, the broker removes only independently provenance-verified previous sidecars by immutable container ID and removes their generated capability files. Remote approval records and business data remain available for reviewed rollback. Docker's embedded loopback DNS is unavailable inside gVisor; trusted exact-network host mappings retain private TLS identity verification.
